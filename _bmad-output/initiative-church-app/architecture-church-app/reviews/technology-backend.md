# Backend technology evidence for Church App architecture

Checked 2026-10-03 against live official Supabase documentation, its changelog, and the npm registry. This is research evidence, not a production provisioning record. No database, project, deployment, or source package was created or changed. No dependency resolution or runtime test was performed.

## Managed platform and versions

- **Supabase managed PostgreSQL 17.11 is a verified greenfield candidate.** The 2026-09-25 release announcement says new projects created from 2026-09-28 use PostgreSQL 15.19 / 17.11. Choose the PostgreSQL 17 line explicitly at provisioning and record the actual managed build then; this evidence does not establish which region/project configuration has been provisioned. The patch includes security changes for `ltree`, `pgcrypto`, `btree_gist`, and custom operator estimators. No existing Church App database objects were found to migrate. Source: <https://supabase.com/changelog/postgres-15-19-17-11-breaking-changes>.
- **Managed extension versions cannot truthfully be pinned through SQL.** From 2026-08-05, explicit `CREATE EXTENSION ... VERSION` and `ALTER EXTENSION ... UPDATE TO` requests are ignored in favor of the instance's default version, with warnings; a future release will reject them. Install required extensions without VERSION clauses, record observed `pg_extension` versions in deployment evidence, and test against the selected managed build. This applies to Cron/pg_net as well as other managed extensions. Source: <https://supabase.com/changelog/extension-version-pinning-ignored> (2026-07-22).
- **Supabase Edge Functions are a managed Deno-compatible TypeScript runtime.** Official platform docs describe this without a user-selectable precise patch pin; the last applicable release in the current changelog records Deno 2.1-compatible rollout to all regions on 2025-08-15. Do not claim a current Deno patch was verified or pin the hosted runtime to an invented exact version. Pin application imports and local tooling; record and smoke-test actual hosted runtime at provisioning and upgrades. Sources: <https://supabase.com/docs/guides/functions>, <https://supabase.com/changelog/37941-all-regions-now-run-deno-2-1-compatible-release>.
- **Per-function dependency config:** official docs recommend each deployed function have its own `deno.json`; shared root config is not recommended for deployment. Exact dependency versions plus committed lockfile are the skill's reproducibility rule; docs' floating `@2` examples are examples, not reproducible project pins. Source: <https://supabase.com/docs/guides/functions/dependencies>.
- **Optional verified TypeScript pins if the implementation selects them:** npm registry returned `@supabase/server` **1.9.0** and `@supabase/supabase-js` **2.117.2** on this date; both declare Node >=22 for Node consumers. The server package uses `@supabase/middleware ^1.0.0` and `jose ^6.2.0`. These are not requirements to introduce a separate Node backend and have not been compatibility-tested in this project's Edge runtime. Sources: <https://registry.npmjs.org/@supabase/server/latest>, <https://registry.npmjs.org/@supabase/supabase-js/latest>. The current Edge auth guide officially demonstrates `npm:@supabase/server@1`; if adopted, exact-pin 1.9.0 and resolve/test its transitive lock before deployment.

## Cron, authenticated workers, and durable jobs

- Hosted Supabase supports `pg_cron` and `pg_net` to invoke Edge Functions on schedules. Vault is the documented place to hold the invocation credential. Source: <https://supabase.com/docs/guides/functions/schedule-functions>.
- **The generic scheduling example is not a secure privileged-worker template.** It currently shows a publishable key as a Bearer token. The newer dedicated auth-header documentation explicitly says publishable/secret keys are not JWTs and belong in `apikey`, while `Authorization` carries a user JWT. A public publishable key cannot prove that a privileged worker request is authorized. Source: <https://supabase.com/docs/guides/functions/auth-headers>.
- Current official service-to-service pattern: a named project secret key in `apikey`; `verify_jwt = false` for that service endpoint; handler validates secret auth, e.g. `withSupabase({auth: 'secret:automations'})`. Disabling JWT verification alone supplies no authorization. User endpoints retain valid user-JWT verification and their domain/session/scope authorization. Do not expose secret keys in clients or log them. Source: <https://supabase.com/docs/guides/functions/auth>.
- `pg_net` dispatch starts **after transaction commit**, but its request/response queues are **UNLOGGED**, are not preserved through a crash/unclean shutdown, and response retention defaults to six hours. Therefore it is a wake-up/transport mechanism, not the canonical durable reminder/job record. Commit domain transition and logged outbox/job insertion/cancellation in one Postgres transaction; a scheduled worker can recover eligible logged jobs after a missed wake-up. Claiming, retries, fencing, attempt history, dedupe, and expiry still require application implementation and tests. Source: <https://supabase.com/docs/guides/database/extensions/pg_net>.
- Cron wakes workers; it does not establish delivery/read proof or exactly-once external effects. No documentation researched establishes exactly-once FCM delivery. Keep logical notification identity separate from uncertain transport attempts, and perform the source revision/current recipient entitlement/actionability checks required by the spec immediately before dispatch.

## API, schema, and authorization constraints

- New projects have explicit table exposure grants by default since 2026-05-30; default-grant removal is enforced for existing projects on 2026-10-30. Creating a table, enabling RLS, and writing policies are insufficient without deliberately granting intended operations to intended API roles. The grant layer and row-policy layer are independent. Existing granted objects retain their grants. Bundle grants, RLS, and policies in reviewed migrations; do not blindly apply broad permissions from an error hint. Source: <https://supabase.com/changelog/45329-breaking-change-tables-not-exposed-to-data-and-graphql-api-automatically> (2026-04-28), <https://supabase.com/docs/guides/api/securing-your-api>.
- Keep custom application tables/functions in application-owned schemas. Since 2025-04-21, creating custom tables/functions or indexes in `auth`, `storage`, and `realtime` is restricted; approved RLS policies/triggers and foreign-key references have documented exceptions. Source: <https://supabase.com/changelog/34270-restricting-access-on-auth-storage-and-realtime-schemas-on-april-21-2025>.
- Realtime's 2026-07-14 restriction prohibits creating, altering, or dropping Realtime-owned objects even as `postgres`; RLS policies on `realtime.messages` remain permitted. Treat Realtime as managed transport, not the home of custom application notification tables. Source: <https://supabase.com/changelog/realtime-schema-locked-down-against-modification>.
- There is a stale documentation conflict: the Storage schema page suggests custom indexes, while the newer reserved-schema restriction expressly forbids new indexes on managed schema tables. Follow the restriction; do not put custom migration-owned indexes there without current provider confirmation. Sources: preceding restriction and <https://supabase.com/docs/guides/storage/schema/design>.
- Database functions default to security invoker; `SECURITY DEFINER` requires deliberate justified design, fixed empty `search_path`, schema-qualified access, and explicit limited EXECUTE grants/revocation of PUBLIC defaults. Current identity, holds, binding, role, and scope checks must survive privileged execution; RLS bypass must never become a business-role bypass. Postgres 15+ views can use `security_invoker=true` to respect underlying policies. Source: <https://supabase.com/docs/guides/database/functions>, <https://supabase.com/docs/guides/api/securing-your-api>.
- JWT role claims are not proof of current permissions. Supabase sessions contain `session_id` linked to `auth.sessions`; strict revocation requires checking whether that session is still active because already-issued access tokens remain cryptographically valid until expiry. Account binding, holds, church approval, scopes, and privileged roles need current server data as the spec requires. Source: <https://supabase.com/docs/guides/auth/sessions>. This does not select a dormancy policy or arbitrary token lifetime.

## Private files, deletion, backups, and restore

- Private buckets support authenticated GET with the caller's Authorization header as well as time-limited signed URLs. Storage policies are on `storage.objects`; upsert needs INSERT + SELECT + UPDATE. Sources: <https://supabase.com/docs/guides/storage/serving/downloads>, <https://supabase.com/docs/guides/storage/security/access-control>.
- **Signed URLs are bearer capabilities with important revocation limits.** They use a separate internal signing key, remain valid through Auth signing-key changes, and cannot be revoked by simply logging out or changing church roles. The Smart CDN page states that cached responses for the same signed URL can outlive token expiry until the response cache TTL expires; deleting the object invalidates cached entries with propagation up to one minute. Immediate-current-entitlement semantics therefore should use authenticated/rechecked file delivery and no-store/private cache behavior, rather than promise signed-URL revocation. Already downloaded bytes cannot be remotely erased. Sources: <https://supabase.com/docs/guides/storage/serving/downloads>, <https://supabase.com/docs/guides/storage/cdn/smart-cdn>.
- Delete file objects through the Storage API. Direct SQL removal of `storage.objects` metadata leaves the underlying blob orphaned. Treat file deletion as a tracked idempotent external job with completion evidence; a database row deletion alone is not full account-content deletion. Sources: <https://supabase.com/docs/guides/storage/management/delete-objects>, <https://supabase.com/docs/guides/storage/schema/design>.
- **Database backups exclude Storage object bytes.** DB backups preserve only object metadata; restoring an old DB backup will not restore objects deleted since that backup. A recoverable application needs a separately verified object-backup/restore process plus database restore and secrets/environment recovery. Source: <https://supabase.com/docs/guides/platform/backups>.
- The backup docs distinguish Pro/Team/Enterprise daily backup retention and optional PITR; free projects are advised to maintain exports/off-site backups. Do not assume a plan, paid PITR, or that a provider database RPO is the whole application's RPO/RTO. Budget, region/data jurisdiction, storage-backup provider, retention, RPO/RTO, and restore ownership remain explicit provisioning/launch decisions.

## Evidence limits

This research verifies documented product behavior and package metadata. It does not verify an existing Church App Supabase project, an actual PostgreSQL build or extension inventory, API grants, RLS, worker concurrency, backups, FCM delivery, or deployment credentials. Those require implementation-time and staging tests. No deployment region, service plan, SMS provider, production retention policy, or numerical service objective is selected here.
