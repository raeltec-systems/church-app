## Intent

**Problem:** AD-20's no-email assisted reset depends on unproven mechanics: trusted detection of native credential changes, generation-bound single-use grants, one privileged mutation in flight per account, and fenced dispatch/completion across a non-atomic Auth Admin call. Assisted recovery must not be enabled until these survive adversarial runs against the deployed Auth version.

**Approach:** Extend the 1.2 harness with (a) a harness-scoped recovery schema on `bic-kafue-auth-test` whose `auth.users` trigger advances the recovery generation atomically with any native credential change, (b) a harness-only Edge Function `harness-recovery` that is the only holder of Auth Admin power and runs begin → fenced dispatch → Admin set + global sign-out → fenced completion, with fault injection, and (c) CLI commands that drive the adversarial runs and write redacted evidence to `evidence-1.3/`.

## Boundaries & Constraints

**Always:** Only project `szfyfezfvxyuvovnnakr`; the function hard-refuses any other `SUPABASE_URL`, JWT issuer/ref or requested project. `verify_jwt` on; every call also needs a harness operator token whose digest is registered in the DB; staff actions need a trusted password session (1.2 predicate) plus staff enrolment. Service key only from the function's platform env. Store only grant digests; grant secrets are generated by the member client, so staff output never holds a usable grant; the member chooses the password and only the function forwards it to Auth Admin. Uncertain/obsolete/late outcomes keep access held until staff reconciliation; resets never clear a security hold. Evidence via harness calls and `attach` of committed read-only queries. Hosted SQL non-destructive.

**Never:** SMS/phone provider configuration; staff seeing a password or usable grant; direct writes to `auth.users`/password hashes; claiming Auth API atomicity; editing `supabase/`, `apps/`, `trials/` or the platform project; more than the minimum Supabase Auth emails.

**Decision (agent, under owner pre-approval):** Accounts are email/password synthetic plus-addresses created through the function's Admin create with `email_confirm` (zero emails); phone-specific rows (phone binding change, phone-only reset identifier) are owner-gated with 1.2's Phone provider step.
**Decision (agent, under owner pre-approval):** Hosted GoTrue v2.197.0 Admin password update does not revoke sessions (source `internal/api/admin.go`), so the function revokes by password-grant with the member-chosen password followed by `/logout?scope=global`; failure of that step is an uncertain outcome.
**Decision (agent, under owner pre-approval):** A credential change seen while an op is dispatched is attributed to that op only when it is the single change and the Auth calls succeeded; otherwise the op becomes `uncertain` (fail closed).
**Decision (agent, under owner pre-approval):** A grant presented with another account's identifier is burned, not merely refused.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Happy reset | issued grant, member chooses password | op succeeded, generation +1, all sessions gone, fresh password login allowed | — |
| Unused grant + direct change | grant issued, member `PUT /user {password}` | trigger advances generation, grant superseded; redeem rejected | generic `grant_rejected` |
| Superseded grant | G1 then G2 issued | G1 rejected, G2 works | — |
| Replay / expired | reuse consumed grant; ttl elapsed | rejected | — |
| Cross-member | A's grant with B's email; staff binds A's member to B's account | rejected and burned; issue refused | — |
| Relink blocked | uncertain op unresolved | relink + new issue `conflict`; after reconcile relink works and old grants die | — |
| Concurrent resets | N parallel redeems of one grant | exactly one op; others rejected | — |
| Pending op + direct change | begin, native change, resume | dispatch fenced → `obsolete`, no Auth call | — |
| Lost response | Auth applied, response lost | op `uncertain`, access held, reconcile needed | — |
| Late external outcome | marked uncertain, Auth applies later | trigger bumps generation, late result recorded, stays held | — |
| Stale completion | replay completion of finished op | rejected | — |
| Hold during reset | hold applied while op in flight | hold applied; success keeps it; probe denied | — |
| Caller auth | no operator token / non-staff / other project | 401/403 refused before any Auth Admin call | — |

## Implementation Notes

- Implemented directly (no subagent tool in this session; the live runs need the MCP tools held here).
- **Hosted changes (auth-test only, all non-destructive):** migrations `auth_harness_005_recovery_fence`, `006_recovery_observe`, `007_db_verified_revocation`; Edge Function `harness-recovery` v1 → v3 (`verify_jwt` true). `sql/002` + `003` are the idempotent sum; hosted `md5` of every function and the trigger equals the committed files applied to a local Postgres 17.11 container (evidence steps `300`/`301`). No approval prompt was cancelled.
- **SQL pre-checked offline** in a throwaway `supabase/postgres:17.11.0.002` container (`--network none`, not the shared local stack, removed afterwards). It caught one bug before the hosted apply (`text[] || 'literal'` → `array_append`).
- **Decision reversed by evidence (agent, under owner pre-approval):** the planned "password grant + `/logout?scope=global`" revocation was wrong for this Auth version. `adminUserUpdate` calls `UpdatePassword(tx, nil)` → `Logout` for the user, in the same transaction (steps `153`/`154`). v3 drops the self-reported revocation (no transient session with the member's password), and `harness_rc_complete` now verifies that no session created before dispatch is still live (`pre_dispatch_sessions_live`).
- **Decision (agent, under owner pre-approval):** grant secrets are generated on the member's device and only their digest is sent (`request`); staff bind the request (`issue`). Staff output therefore never holds a usable grant (`staff_output_contains_secret:false` on every issue line).
- **Decision (agent, under owner pre-approval):** harness-caller authentication = `verify_jwt` + own-project issuer/ref + an operator token registered by digest (8 h expiry) via MCP; staff actions additionally need 1.2's trusted password session and staff enrolment; member actions use the legacy anon key because a member in recovery has no session.
- **Decision (agent, under owner pre-approval):** database state is recorded raw through a staff-only `observe` action wrapping `sql/observe_recovery_state.sql`, avoiding hand-transcribed MCP output.
- **Emails:** zero. Accounts were created by Auth Admin with `email_confirm`.
- **Findings** for identity are in `evidence-1.3/README.md` (Admin update revokes sessions; count-based attribution; reconcile is a manual decision; the 1.2 probe alone is not the gate; advisor notes).
- **Owner-gated rows:** phone binding change and phone-only reset identifier wait on 1.2's Phone provider step; native email-change detection is deferred to the same rerun to respect the ~2 emails/hour limit.
- Evidence quirks (documented in the evidence README): the phase-1 label key `grant` was over-redacted (renamed `grant_label`); steps `210`/`211` used a stale local password and the happy path was re-run as `240`–`248`.
